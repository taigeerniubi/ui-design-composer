# 组件点击、进行中、结束与恢复

## 分开两类状态

**输入反馈**表示用户正在怎样操作控件：默认、悬停、键盘焦点、按下、持续选中或禁用。

**任务状态**表示操作实际进行到哪里：就绪、校验、提交、排队、执行、成功、失败，或按任务需要出现的取消、部分完成、结果未知。

两者可以同时存在。例如请求已在进行中，取消按钮仍可获得焦点；鼠标已松开，保存任务仍在执行。CSS `:active` 的短暂按下反馈和开关按钮 `aria-pressed` 的持续切换语义也要区分。

即时展开、切换等本地操作可以直接进入新状态，不必人为插入加载过程。只设计实际需要的状态。

## 输入反馈

| 状态 | 显示与行为 |
| --- | --- |
| 默认 / Rest | 文案、外观和可点击区域说明用途与可用性；导航用链接，执行动作用按钮。 |
| 悬停 / Hover | 可通过颜色、边界或轻微变化增强反馈；必要信息与操作不能只靠悬停出现。 |
| 键盘焦点 / Focus-visible | 焦点清晰，不被裁切或遮挡；检查实际背景。触屏仍有完整入口。 |
| 按下 / Pressed | 按下时给局部反馈；不因此变成成功状态或移动整个页面。 |
| 选中、展开或开关 | 持续显示当前值，使用与组件匹配的语义，例如 selected、expanded、checked 或切换按钮的 pressed。 |
| 禁用 / Disabled | 阻止实际动作，必要时在可发现位置说明原因。`aria-disabled` 本身不阻止事件；只读内容仍可阅读或复制，和禁用区分。 |

原生按钮支持键盘激活，避免同时在键盘和点击处理器中重复触发。打开弹窗时移入适当焦点，关闭后通常返回触发处；原地应用变更时通常保留当前上下文。按钮、切换语义及焦点规则参考 [WAI 按钮模式](https://www.w3.org/WAI/ARIA/apg/patterns/button/)。

## 任务进行与结束

| 阶段 | 用户看到什么 | 操作与数据规则 | 如何离开此状态 |
| --- | --- | --- | --- |
| 就绪 / 校验 | 动作名称、必要条件、字段级提示 | 校验失败不丢输入；避免用户尚未输入就不断报错 | 校验通过后执行；未通过时引导修正 |
| 提交 / Pending | “提交中…”等明确反馈，避免重复点击误解 | 防止同一次动作重复提交；只限制相关冲突操作，保留原布局与输入 | 得到受理、结果、错误或可识别的中断信息 |
| 排队 / Queued | 确有队列时显示“等待处理”，有可靠信息才显示位置 | 区分已受理与已执行；提供后续查询或实际可用的取消 | 任务开始，或后端确认失败、取消 |
| 执行 / Running | 真实阶段、可计算的进度，或明确的不定进度 | 不编造百分比；进度满格不能代替最终结果；保留必要取消或后台入口 | 获得实际完成、失败或取消结果 |
| 成功 / Success | 完成对象、结果与下一步，如“查看文件”“继续编辑” | 依据真实返回值更新内容与保存状态，提供适当撤销；允许下一次合法操作 | 进入结果或就绪状态，保留必要完成记录 |
| 失败 / Error | 可理解的原因与恢复入口，必要时保留详细信息入口 | 保留输入及已成功部分；说明重试范围，避免只闪过短暂提示 | 修正后重试、重新选择、返回或明确放弃 |
| 请求取消 / 已取消 | 先显示“正在取消”；获得确认后再显示“已取消” | 说明部分结果是否保留；关闭弹窗不等于取消真实任务 | 取消确认后可重新开始；若完成先到，显示实际结果 |
| 结果未知 / Timeout | “连接中断，正在确认结果”等符合事实的状态 | 不把网络超时直接等同于失败；可能重复创建的动作先查询再重试 | 确认结果，或给出明确的人工处理和查询入口 |
| 部分完成 / Partial | 完成与失败数量，以及对应条目 | 保留成功结果，仅对适合重试的失败项提供重试 | 处理剩余条目，或接受当前结果结束 |

“成功”需要内容与状态共同更新。只出现绿色提示、进度消失或按钮恢复正常，都不足以让用户理解是否得到结果。重要结果应有可再次查看的入口，不全部依赖短暂消息。

## 关键组件的覆盖范围

| 组件 | 需要具体决定的状态 |
| --- | --- |
| 按钮、保存与提交 | 默认、焦点、按下；异步时的处理中、重复触发限制、成功后可再操作、失败后重试。 |
| 输入框与表单 | 空值、输入、只读或禁用、校验时机、错误解释、提交中与结束后保留内容。 |
| 上传区域与文件条目 | 选择与拖入、校验、上传、后续处理、逐项成功或失败、真实取消；重试时保留成功文件。 |
| 弹窗与抽屉 | 打开、焦点进入、编辑未保存、提交中能否关闭、失败是否继续展示、关闭后焦点与后台任务归属。 |
| 开关与即时设置 | 原值、切换反馈、保存中与保存失败；乐观更新失败时回滚并解释，或清楚标示尚未保存。 |
| 下拉、标签页与导航 | 打开或选中、键盘操作、加载目标内容、加载失败与返回；切换不误清空输入。 |
| 搜索、列表与表格 | 首次加载、刷新、空数据、筛选无结果、错误、部分数据与恢复；不把“无结果”当成请求失败。 |
| AI 生成与长任务 | 提交、排队、阶段或流式输出、停止请求、实际停止、部分结果、完成和失败；区分已生成与已保存。 |

## 实现时的边界

- 重复触发保护以同一动作及对象为范围；涉及创建或其他不可重复操作时，结合已有接口的幂等或结果查询能力处理。UI 禁用按钮不能替代接口保证。
- 对象或筛选已改变时，旧响应不能覆盖当前上下文；提交期间如允许继续编辑，明确保存的是哪个版本，较早请求完成不能把后来修改标成“已保存”。
- 可逆且可恢复的任务可考虑乐观更新，并定义失败回滚。需要真实结果确认的任务不能提前显示已完成。
- 结束或异常后释放相关忙碌状态与重复触发限制；校验错误仍在时保持合适限制，不能所有结束情况一律启用按钮。
- 动画用于表达状态，尊重减少动态效果偏好。避免循环动画长时间承担唯一进度解释，也不为每次悬停强制位移。

## 无障碍状态与焦点

状态消息可使用适合的 `role="status"` 或 `aria-live="polite"`；需要及时处理的错误再考虑告警语义，避免每个微小进度都打断用户。忙碌区域按实际更新过程使用 `aria-busy`，并在结束时复原；不要把完成消息一直包在仍为 busy 的区域内。

状态告知与内容更新要配合，避免随意抢焦点。提交后需要定位错误时，使错误字段及所在折叠区域可见；关闭或移除组件后，焦点回到合理的操作上下文。

依据：[W3C 状态消息说明](https://www.w3.org/WAI/WCAG22/Understanding/status-messages.html)、[MDN aria-busy](https://developer.mozilla.org/en-US/docs/Web/Accessibility/ARIA/Reference/Attributes/aria-busy)。

## 状态交付与验证

为关键操作用一行或多行记录：

```text
触发条件 | 当前状态及文案 | 允许操作 | 数据与焦点变化 | 完成依据 | 下一状态与恢复
```

在真实接口或隔离的可控模拟中检查正常完成、失败、重复触发，以及确实适用的中断和恢复。模拟结果要标明；模拟不能声称验证了真实服务。涉及长文案、处理中按钮和错误提示时，同时查看字体折行、颜色角色和布局稳定性。
